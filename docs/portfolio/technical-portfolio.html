01 — Overview

DBを持つWebサービスを、画面からデプロイまで一人で作り切る

inustaは、認証・投稿・コメント・画像保存を備えたフルスタックのSNSです。この1作品で示せる力を整理しました。

サービス概要

対象
愛犬の写真を気軽に残し、共有したい飼い主
目的
写真の投稿とコメントで、飼い主同士がゆるく交流できる場をつくる
形態
自社サービス型のWebアプリ（PC・スマホ対応）
公開
Vercelにデプロイし、PostgreSQLとVercel Blobに接続

認証・認可

Auth.jsのCredentials認証とMiddlewareでのルート保護。更新・削除はサーバー側で所有者を確認。

DB設計・CRUD

PrismaでUser・Post・Commentの1対多を定義。一覧・詳細・作成・編集・削除を実装。

03 — Architecture

技術構成：読み取りはServer Components、書き込みはServer Actions

APIを別サーバーに立てず、Next.js（App Router）の中でDB・ストレージ・認証までつなげています。

技術役割
Next.js / React画面とサーバー処理を1つのアプリで実装
Middlewareログイン必須ページへの未認証アクセスを遮断
Server Actionsフォーム送信を受け、検証・保存・再描画まで行う
Zod登録・ログイン入力の形式を実行時に検証
Auth.js / bcryptメール＋パスワード認証、ハッシュ照合
Prismaスキーマ定義から型付きのDB操作を生成
PostgreSQLユーザー・投稿・コメントを保存
Vercel Blob画像ファイルを保存し公開URLを返す

※ 例外として、ヘッダーのユーザー表示用に Route Handler GET /api/me を1本用意しています。

データ設計と、機能ごとの処理

3つのモデルを1対多でつなぎ、ユーザーや投稿を削除すると関連データも連鎖削除される構造にしました。

機能主な処理
会員登録Zod検証 → メール重複確認 → bcryptでハッシュ化 → User作成 → 自動ログイン
ログインZod検証 → Userを取得 → bcrypt.compare → セッション発行
投稿作成認証 → 画像の形式・サイズ検証 → Blob保存 → Post作成
投稿編集・削除投稿ID と ログインユーザーIDの両方で絞り込んで更新・削除
コメント投稿の存在確認 → Comment作成 → 詳細ページを再検証

05 — Authentication & Authorization

認証・認可：「ログインしているか」と「本人の投稿か」を分けて守る

画面の入口はMiddlewareで、データの書き換えはServer Actionの中で、それぞれサーバー側で確認しています。

1ログイン（認証）
2ページ単位のアクセス制御（Middleware）
アクセス先未ログインログイン済み
/・/login・/register表示/dashboard へ
上記以外（投稿・マイページ等）/login へ表示
/register/complete登録直後の遷移を妨げないよう常に表示
3データ単位の認可（Server Action）

編集・削除は、投稿IDだけでなくログインユーザーのIDも条件に含めてDBを操作します。画面のボタンを隠すだけでは、フォームを直接送られると防げないためです。

06 — Key Flow

代表処理：画像付き投稿の作成

フォーム送信から画面更新まで、1つのServer Actionの中で「認証 → 検証 → 保存 → 再描画」を順に行います。

バリデーションの置き場所

対象ブラウザサーバー
投稿画像形式・5MB・プレビュー形式・サイズ
会員登録—Zod：必須・形式・8文字以上・確認一致・重複
ログイン—Zod＋bcrypt
コメント—未入力チェック

ブラウザ側は使いやすさのため、最終判断は必ずサーバー側で行う方針です。

Blobを先に保存する理由

Postの image は必須項目のため、先にBlobへ保存してURLを確定させてからレコードを作成します。これにより「画像のない投稿」がDBに残りません。

07 — Problem Solving

問題解決：見つけた課題と、その対応

実装・デプロイ中に発生した課題を「課題・対応・結果」の3行で整理しました。

セキュリティ

他人の投稿を書き換えられないようにする

課題
編集・削除ボタンを本人にだけ表示しても、投稿IDを指定したリクエストを直接送れば操作できてしまう。
対応
Server Actionでセッションからユーザーを特定し、where: {id, userId} で更新・削除するよう変更。
結果
所有者以外の操作はDBで一致せず失敗し、画面の作りに依存せずサーバー側で守れるようになった。
不具合修正

投稿時に選んだ画像が消える

課題
プレビュー表示に切り替える際にfile inputがDOMから外れ、送信時に画像が含まれないことがあった。形式・サイズの制限もなかった。
対応
inputを常に描画したまま見た目だけ切り替え、画像削除時は値をリセット。Server Actionに形式・5MBの検証を追加。
結果
画像が確実に送信され、想定外のファイルはサーバーで弾かれるようになった。
デプロイ

本番環境でDB・画像がつながらない

課題
Vercelで発行される接続用の環境変数名とPrismaの参照先が食い違い、本番でDBに接続できなかった。Blob画像もnext/imageで表示できなかった。
対応
ログで実際の値を確認しながら接続先を DATABASE_URL に統一。BlobのドメインをremotePatternsに登録。
結果
ローカルと本番で同じ設定名で動くようになり、画像も最適化された状態で配信できた。

08 — Design Decisions

設計上の判断

「なぜその方法を選んだか」を説明できるように、主な判断を残しています。

構成REST APIを作らずServer Actionsを採用

画面とサーバー処理を同じアプリ内に置けるため、APIの型定義やfetch処理を二重に書かずに済みます。読み取りは lib/apis.ts、書き込みは lib/actions.ts にまとめ、役割で分けました。

UX無限スクロールは重複を防いで追加

初回20件をサーバーで描画し、末尾が見えたら IntersectionObserver でServer Actionを呼んで次の20件を取得。読み込み中フラグで二重リクエストを防ぎ、IDで重複を除外して結合します。

表示Suspense＋スケルトンで待ち時間を見せる

DB取得を行うコンポーネントを Suspense で囲み、読み込み中はレイアウトに合わせたスケルトンを表示。ヘッダーやナビゲーションは先に表示されます。

安全取り消せない操作は一度確認する

投稿削除は「Danger Zone」として編集画面の下部に分離し、確認モーダルを挟んで実行。プロフィールや投稿の編集も送信前に内容を確認できるようにしました。

データ必要な列だけを取得する

Prismaの select で画面ごとに取得列を指定し、パスワードハッシュなど不要な値がクライアントへ渡らないようにしています。コメント数は _count で一覧と同じクエリ内で取得。

開発シードデータで画面を確認しやすく

Prismaのseedで10ユーザー・100投稿・1,000コメントを投入できるようにし、一覧・追加読み込み・詳細の表示確認を実データに近い量で行えるようにしました。
